# Cycle 2026-11-04 — Forgejury

**Idea:** *Forgejury* — one stdlib-Python gate on the build→review handoff. It
reads a machine-readable **acceptance block** the reviewer authored in the spec,
independently re-observes each build's state, diffs that against what each build
*claimed* (`claims.json`), and diffs the three builds against each other on a
thin-waist `invoke` contract. One triangulated verdict instead of reading three
build folders top-to-bottom.

**Verdict: SHIP. Winner: exec-2.** Two of the three builds (exec-1, exec-2) are
correct, honest, stdlib-only, and pass both their own demo and a live dogfood
against this cycle's real `SPEC.md`. exec-3 is the most inventive but carries a
real correctness bug on the actual target spec.

## How they compare

All three: `python -m forgejury lint|grade` with `--json`, zero third-party
imports (only stdlib + `from __future__ import annotations`), both honesty
statements verbatim in the README, Layer 3 (fence) correctly dropped per spec.
I ran every demo command and the test suite myself; numbers below are observed,
not reported.

### exec-1 — minimalist, correct, lean
Single ~357-line `__main__.py`, 8 passing tests. Demo reproduces exactly as
reported: honest build all-PASS, lying build `FAIL` naming the lie
(`extra_module.py`, `tests_passed claimed 5, observed 2`), 2-1 consensus split
on `add-big` naming `build-c`. Parses the acceptance block robustly
(`^## Forgejury Acceptance Block$` MULTILINE, takes the **last** match) so it
grades the real SPEC correctly. Nice gate semantics: a claims-axis lie flips the
per-build verdict to `FAIL` and the process exits non-zero. Thin test coverage
and no distinguishing twist keep it from the top slot.

### exec-2 — production engineer, the winner
Modular (10 files), **41 tests**, richest `--json` (per-fixture `label`,
`diverging_build`, `expected_match`, `outputs`, `errors`). Demo reproduces
exactly. It is the most robust against the two real traps in the actual spec:
- It anchors the heading match and takes the **last** occurrence, so it does not
  confuse the prose mention of `## Forgejury Acceptance Block` (inside the "Data
  formats" section) with the real heading at the bottom. It explicitly flagged
  this trap in its build-report — and exec-3 fell into exactly it.
- It keeps the `--json` `build` field as the literal caller string rather than
  round-tripping through `pathlib` (which on Windows turns `a/b` into `a\b`).

One debatable call: a claims-axis lie does **not** flip the build's top-level
`verdict` to `FAIL` (it stays `PASS`, lie shown only in the claims axis). The
spec treats the claims axis as advisory, so this is defensible, but exec-1's
louder stance is arguably safer for a gate. Minor.

### exec-3 — wild experimentalist, best demo, real bug
The most inventive: a literal ASCII **triangulation** diagram summarizing
pairwise fixture agreement (a real computed aggregate, degrades under
`NO_COLOR`), and the richest self-demo — 5 fixtures including a genuine **3-way**
split and pinned-`expected` failures, the only build to actually exercise every
consensus class. Its own demo and 31 tests are all green.

**But it breaks on the real spec.** Its block parser uses a plain
`spec_text.find("## Forgejury Acceptance Block")` (first substring match), so
when I dogfood-graded it against this cycle's `builds/2026-11-04/SPEC.md` it
parsed the **illustrative placeholder** block in the prose
(`requires_file: ["path/relative/to/build/dir"]`,
`requires_symbol: module.py::symbol_name`) instead of the real acceptance block,
and reported everything `FAIL`. It stays green only because its bundled
`examples/SPEC.md` contains the heading exactly once. This is precisely the
silent bug exec-2 predicted. It dents "works when run" on the primary dogfood
use case.

## Live dogfood (the real triangulation)

Using exec-2's Forgejury to grade all three builds against this cycle's actual
`SPEC.md` acceptance block:

```
$ cd builds/2026-11-04/exec-2
$ python -m forgejury grade ../SPEC.md ../exec-1 ../exec-2 ../exec-3
[exec-1] verdict=PASS   spec axis: all PASS   claims axis: all PASS
[exec-2] verdict=PASS   spec axis: all PASS   claims axis: all PASS
[exec-3] verdict=PASS   spec axis: all PASS   claims axis: all PASS
=== Consensus (behavioral, stdout-only) ===
  triangulated-verdict: 3-way
      error[exec-1]: exit 1
```

Every build satisfies the real spec axis (all four required files, the `main`
symbol via `ast`, `pytest` exits 0) and has an honest `claims.json`. Consensus
is `3-way` because each build's human-facing `--json` differs in shape — expected
across three personas. A genuinely useful signal fell out of it: the gate caught
that exec-1 exits non-zero when a build verdict is `FAIL`, so as a nested
subprocess it registered as `error[exec-1]: exit 1`. The tool found a real
behavioral difference between the builds — exactly its job.

## How to run the winner (exec-2)

```
cd builds/2026-11-04/exec-2
python -m forgejury lint examples/SPEC.md
python -m forgejury grade examples/SPEC.md examples/build-a examples/build-b examples/build-c
python -m forgejury grade examples/SPEC.md examples/build-a examples/build-b examples/build-c --json
python -m pytest -q        # 41 passed
```

`lint` warns on the volatile (date-shaped) fixture; `grade` shows build-a
all-PASS, build-b's claims axis `FAIL` naming `CHANGELOG.md` and
`tests_passed claimed 5, observed 1`, and an `add-negative` 2-1 split naming
`build-c`.

## What I'd do next

1. **Wire the winner into `forge.py`** so every future `review` stage runs
   `forgejury grade <SPEC.md> <exec dirs> --json` automatically and I start from
   its table — this cycle proves it reproduces what I found by hand.
2. **Harvest the best of the losers.** Graft exec-3's triangulation diagram onto
   the human-readable output (it genuinely speeds the ~30-second read), and adopt
   exec-1's stance that a claims-axis lie flips the top-level verdict to `FAIL`.
3. **Add a shared regression fixture** for the duplicate-heading trap to whatever
   ships, since it bit one of three builds silently.
4. **Fix the spec's own acceptance block** next cycle: its `consensus.invoke`
   omits the `{input}` placeholder, which a strict `lint` (exec-1's) rightly
   rejects. Either add a no-op `{input}` or let `lint` allow empty-input
   fixtures.
