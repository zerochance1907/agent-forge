# Cycle 2026-11-18 — BuildOracle

## The idea

**BuildOracle** — a behavioral-diff gate for agent refactors. A small, stdlib-only
Python CLI that records a module's `(input → return/raise)` behavior, then, after
an agent rewrites that module, replays the recording and **vetoes any divergence**.
Its novel wedge is honesty about its own limits: before gating, it *classifies*
whether the module is deterministically gateable at all (static AST scan **plus**
an empirical double-run), and **refuses** — rather than emitting a flaky pass/fail —
when it can't be sure. Four pinned cases demonstrate the four outcomes:
`identity → PASS`, `offbyone → FAIL`, `nondeterministic → REFUSE`,
`keyorder → PASS` (passing only because canonicalization sees through key order).

Target user: any coding agent (or human) doing a refactor who wants a cheap,
offline safety net that won't cry wolf.

### What each got right and wrong

**exec-1 — minimalist, clean, functionally complete.** 187-line core, 11 tests,
no clutter. Every verdict correct, all three `verify` exit codes reachable
(its `verify` cleverly re-runs the static scan so it can REFUSE without a fresh
exercise script). The one real miss: it prints the coverage line with an ASCII
`--` instead of the spec's em-dash `—`, so it does not emit criterion 6's **exact**
string. A deliberate, portable choice — but not what the spec pinned. claims.json
is accurate.

**exec-2 — production engineer, the most rigorous.** 288-line core, 21 tests
(the most), including subprocess-level CLI tests that actually assert the
`gate` stdout contract and the `verify` exit codes. It is the **only** build that
emits the spec's exact coverage line correctly on Windows: it caught that
Windows' default cp1252 codepage mangles the em-dash and fixed it by
reconfiguring stdout/stderr to UTF-8 — then flagged in its report that the other
two builds might have gotten lucky. It had. claims.json is accurate. This is the
build that treated the spec text as a contract down to the byte.

**exec-3 — wild experimentalist, the most creative, the least disciplined.**
260-line core plus a separate `oracle_eye.py` presentation layer. Its `demo` is
genuinely the best *teaching* artifact: ASCII "oracle" sigils per verdict, and for
the `keyorder` case a **live proof** printed from that run's real `repr()` and
`canonicalize()` calls showing the raw reprs differ but the canonical forms match —
exactly the point the whole tool rests on. But it has the two problems the other
builds avoided:
1. **Encoding bug.** It writes the em-dash but does *not* reconfigure stdout to
   UTF-8, so on Windows the coverage line emits byte `\x97` (mojibake `�`) — the
   exact bug exec-2 warned about. Criterion 6's exact string fails on this machine.
2. **Dishonest claims.json (caught by Forgejury).** It claims `tests_passed: 16`
   but 19 run, and its acceptance notes claim `verify` exit-20 "is not exercised by
   any test or CLI path" — yet I ran `verify` on a nondeterministic module and it
   returned exit 20 cleanly. Both discrepancies are *understatements* (pessimistic/
   stale, not flattering), so this is sloppiness rather than gaming the grader — but
   claims.json is supposed to be the build's honest self-report, and this one is
   wrong twice.

## Winner: exec-2

It passes everything the spec pinned, is the only build that gets the one
cross-platform correctness detail right (the exact coverage string on Windows),
carries the most thorough test suite, and its claims.json is honest. exec-1 is a
clean, close second that fails only the em-dash exactness. exec-3 is the most
inventive and would be the best thing to *show* someone — but it ships a real
Windows encoding regression and a claims.json that Forgejury caught disagreeing
with reality.

## How to run the winner

```
cd builds/2026-11-18/exec-2
python -m buildoracle demo        # table: identity PASS, offbyone FAIL, nondeterministic REFUSE, keyorder PASS
python -m pytest -q               # 21 passed
python -m buildoracle gate --case offbyone   # {"verdict": "FAIL"}  (exit 0)
```

## What I'd do next

The idea is sound and demonstrably buildable; this ships. If we iterate on it
later rather than shipping as-is, two directions:
- **Steal exec-3's demo into exec-2's engine.** exec-2 has the correct, honest
  engine; exec-3 has the far more persuasive demo (the live canonicalization
  proof). The best single artifact is exec-2's core with exec-3's `oracle_eye`
  presentation layer bolted on (and UTF-8 reconfigure kept).
- **Harden `verify`'s standalone REFUSE.** All three made `verify` re-derive
  gateability so it can REFUSE without a fresh exercise script — a sensible
  resolution of a spec gap, but it means `verify` silently re-runs the static
  scan. Worth making that explicit in the next spec rather than leaving each
  builder to invent it.
